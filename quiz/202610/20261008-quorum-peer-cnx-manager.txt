第 1 题 [概念理解] ★
QuorumPeer 中同时存在 ServerState（字段 state）和 LearnerType（字段 learnerType）两个枚举。
(1) 分别写出它们的取值；
(2) 说明二者语义上的区别：哪个是"会随运行变化的"，哪个是"配置决定、基本不变的"？
(3) 一个配置为 observer 的节点，在正常运行过程中 state 会经历哪些取值？它会不会进入 LEADING / FOLLOWING？
提示：看 LearnerType 上方的注释，以及 QuorumPeer#run 中 LOOKING 分支如何决定下一步状态（可顺带看 FastLeaderElection 中对 learnerType 的判断）。

【我的答案】
(1) state 取值：looking , following, leading, observing;
    learnerType 取值: participant, observer.
(2) state 是会变化的：每个Peer在启动时，都是looking状态，走完选举流程之后，成为leader的节点为leading状态，成为follower的节点
    为 following 状态；
    learnerType 不会变化：这个字段来源于配置 org.apache.zookeeper.server.quorum.QuorumPeerConfig.peerType，peerType取配置文件
    中 peerType；当 peerType = 'observer' 时，learnerType = 'observer', peerType 默认值为 participant。
    // 代码段如下：
    else if (key.equals("peerType")) {
        if (value.toLowerCase().equals("observer")) {
            peerType = LearnerType.OBSERVER;
        } else if (value.toLowerCase().equals("participant")) {
            peerType = LearnerType.PARTICIPANT;
        } else
        {
            throw new ConfigException("Unrecognised peertype: " + value);
        }
    }
(3) 从 LearnerType doc 以及 QuorumPeer#run 方法判断：
    一个配置为 observer 的节点，在运行过程中仅仅会经历 looking 和 observing 两个状态。
    在 QuorumPeer#run 方法中 while 主循环中，当 observing 的状态发生变化时，在finally块中设置了 state = looking.
    所以 observer 节点主要在 looking 和  observing 两个状态切换。

第 5 题 [流程梳理] ★★★
以 FastLeaderElection 发出一张选票为起点，描述消息经过 QuorumCnxManager 发往对端、再被对端选举线程读到的完整路径。要求覆盖：

提示：注意 SendWorker#run 刚启动时会先做一件"补发"的事。

【我的答案】
FastLeaderElection的核心方法在lookForLeader()，内部有一个主循环。
FastLeaderElection发选票时：
(1) 封装ToSend，包括当前选择的主节点和zxid和当前节点的状态，并放到sendqueue队列有WorkerSender线程消费；
(2) 发送线程WorkerSender从队列中取出ToSend，封装为ByteBuffer，并提交给QuorumCnxManager的toSend方法；
(3)
// 保存从当前节点到其它各个节点的发送线程和TCP连接，key是sid
final ConcurrentHashMap<Long, SendWorker> senderWorkerMap;
// 每个连接一个队列，用于保存需要发送的消息，key是sid
final ConcurrentHashMap<Long, ArrayBlockingQueue<ByteBuffer>> queueSendMap;
// 记录发送给每个节点的最后一条消息，key是sid，用于补发
final ConcurrentHashMap<Long, ByteBuffer> lastMessageSent;
(4) initiateConnection 建连时，首先写当前节点的sid，用于对方判断是否重新建立连接；因为集群连接遵循从大sid发起的规则
(5) 消息长度+消息体
(6) 先读消息长度，然后安装长度读取消息体，放到recvQueue

第 10 题 [设计思考] ★★★
QuorumCnxManager 的设计中有几处"看起来不严谨"的取舍：
- toSend 中当发送队列满（remainingCapacity()==0）时直接 bq.take() 丢弃最旧消息；
- 每对 server 之间只保留一条 TCP 连接，由 sid 大小决定方向；
- SendWorker 启动时无条件重发 lastMessageSent 中的最后一条消息。
请分析：
(1) 为什么在选举场景下"丢旧消息"是可以接受的？如果换成 Leader-Follower 之间的 PROPOSAL/COMMIT 同步通道，还能这样做吗？
(2) 重发最后一条消息解决了什么问题？会不会导致对端收到重复选票，FastLeaderElection 能否容忍？
(3) toSend 里 "containsKey → put" 两步不是原子的，在什么并发情况下可能出问题？你会如何改进？

【我的答案】
(1) bq.take()之后会加上最新的消息；ROPOSAL/COMMIT 同步通道不可以
(2) 重发最后一条消息解决 发送时连接断掉等，
(3) toSend目前只有线程单线程调用，多线程情况下会出现race condition
java.util.concurrent.ConcurrentMap.putIfAbsent

点评：
    答对的部分：
        发送链路前半段（ToSend → sendqueue → WorkerSender → manager.toSend）、
        三个 Map 的作用、8 字节 sid、"长度 + 消息体"格式。
    漏掉的部分：
        - toSend 中 sid == 自己时的 loopback；

参考答案：
    - toSend：
        self.getId() == sid 时不走网络，
        b.position(0) 后直接 recvQueue.put(new Message(b.duplicate(), sid))，
        即自己给自己的选票直接放进接收队列；
        否则把 b 放入 queueSendMap.get(sid)（满了先 take 掉最旧的一条），然后 connectOne(sid)。
    - connectOne：
        senderWorkerMap.get(sid) == null 时才建连，连接 electionAddr，再 initiateConnection。
    - initiateConnection：
        先写 8 字节 long 的 self.getId()；
        若对方 sid 更大则关闭自己发起的连接，
        否则创建 SendWorker / RecvWorker 并放入 senderWorkerMap。
    - SendWorker#run：
        先把 lastMessageSent.get(sid) 重发一次；
        再循环 queueSendMap.get(sid).poll(1000ms)，取到后先 lastMessageSent.put 再 send。
        send 的报文格式 = 4 字节 int（b.capacity()）+ 消息体。
    - RecvWorker#run：
        循环读满 4 字节长度；
        length <= 0 或 length > PACKETMAXSIZE（1024*1024）时抛 IOException 断开；
        再读满 length 字节消息体，封装成 Message(message, sid) 放入 recvQueue。
    - 之后：
        FastLeaderElection 的 WorkerReceiver 通过 manager.recvQueue.poll(3000ms) 取出，
        反序列化为 Notification 放入 recvqueue，供 lookForLeader 消费。

第 10 题：5/10 —— 部分正确
点评：
    三问都只给了结论，缺少原因；
    (3) "toSend 只有单线程调用"的前提不完整。
参考答案：
    (1) 选举中每台机器只关心对方的最新选票，新通知会覆盖旧通知；
        而且 lookForLeader 在 poll 超时后会 sendNotifications() 或 connectAll() 重发，
        丢掉旧消息不影响正确性。
        PROPOSAL/COMMIT 要求可靠、有序、不丢（ZAB 依赖 FIFO 的 TCP 通道），
        丢一条就会造成数据不一致，所以不能这样做。
    (2) 连接断开时，最后一条消息可能已经从队列取出、但对端还没收到。
        新连接建立后，SendWorker 先补发 lastMessageSent，避免这条选票丢失。
        重复选票可以容忍：lookForLeader 对收到的通知用 totalOrderPredicate 比较，
        并以 recvset.put(n.sid, ...) 按 sid 覆盖，重复处理同一张选票结果不变（幂等）。
    (3) toSend 确实只由 WorkerSender 单线程调用，
        但 queueSendMap 的 containsKey → put 还出现在：
            - initiateConnection（QuorumPeer 线程经 connectAll/connectOne、WorkerSender 经 connectOne）；
            - receiveConnection（Listener 线程）。
        如果 toSend 刚 put 了新队列并放入消息，receiveConnection 同时判断 !containsKey
        也 put 了一个空队列，就会把 toSend 的队列连同消息一起覆盖掉。
        改进：统一用 queueSendMap.putIfAbsent(sid, new ArrayBlockingQueue<ByteBuffer>(CAPACITY))，
        之后再 get。
