QuorumCnxManager 同时互连竞态

ZooKeeper 3.3.6。A（sid=1）和 B（sid=2）同时向对方发起连接时，已经收敛好的连接 X 会被 B 误杀，然后重建为连接 Z。最终仍然只有一条连接，但中间多了一轮无意义的断连和重连。

时序图

连接 X（B→A，本来是好的） 连接 Y（A→B，按规则应丢弃） 误杀 X 重建的连接 Z（B→A）

各时刻两端的连接状态

时刻A.map[2]B.map[1]发生了什么
t1—SW_B1(X)B 发起的 X 赢得比较，B 保留
t2—SW_B1(X)A 发起的 Y 比较输了，A 关闭 Y
t3SW_A1(X)SW_B1(X)已经收敛到 1 条连接 X
t4SW_A1(X) 已失效SW_B2(Z)B 处理迟到的 Y，误杀 X，再发起 Z
t5空SW_B2(Z)A 的 RecvWorker 读到 EOF，清理 SW_A1
t6SW_A2(Z)SW_B2(Z)再次收敛到 1 条连接 Z

为什么会误杀

receiveConnection 在对端 sid < 我的分支（QuorumCnxManager.java:254-272）里，不管现有连接是不是刚建好的，都会先 finish 掉。这段逻辑的本意是处理对端重启，但它分不清下面两种情况：

  • 对端重启后发来新连接，旧连接确实已失效
  • 和 X 同时发起、只是晚到一步的 Y，X 其实是好的

后果

  • 消息延迟：已经写进 X 的投票可能丢失，要等新的 SendWorker 启动时重发 lastMessageSent 才能补上
  • Listener 被卡住：t4 的 connectOne 在 Listener 线程里同步执行，还要和 WorkerSender 争同一把锁，期间无法接收其他节点的连接

实测：CnxManagerTest.testCnxManager 日志

日志见 notes/CnxManagerTest_testCnxManager.txt。测试里 s0（sid=0）相当于上图的 A，s1（sid=1）相当于 B。决定会不会误杀的，是 s1 上两个线程的先后顺序：Listener 处理迟到连接 x1 时调用的 get(0)，和 main 线程把 y1 的 SendWorker put 进 map，谁先发生。

在日志里复现

同时启动两个节点，在 sid 较大一方的 DEBUG 日志里按顺序找这三条：initiateConnection ... established → Calling finish on SendWorker → Create new connection Back to server: …。再用 SendWorker 日志里的 identityHashCode 区分新旧 worker。如果 Create new connection Back 前面没有 Calling finish，说明这次 get 先于 put，没有踩中竞态，就像上面实测的第 48 行。
