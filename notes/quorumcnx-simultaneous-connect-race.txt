QuorumCnxManager 同时互连竞态时序（ZooKeeper 3.3.6）
====================================================

一、先更正一个说法
----------------
之前认为 "get -> finish -> put 非原子，可能导致短暂多出 worker"，这个说法不成立。原因有两点：

1. 对同一个对端 sid，本机只会在一个地方执行 put：
   - 对端 sid > 我：只有 receiveConnection 会放入新 worker，它只在 Listener 线程里执行（单线程）；
   - 对端 sid < 我：只有 initiateConnection 会放入新 worker，它只从 synchronized connectOne 里调用。
   所以同一个 sid 的 put 本身就是串行的。
2. SendWorker.finish() 是 synchronized 的，并用 running 标志保证只执行一次。
   旧 worker 总是先 finish、新 worker 再 put，所以旧 worker 后续再调 finish() 时会直接返回，
   不会走到 remove(sid) 把新 worker 删掉。

代码里实际存在的竞态是另一种：双方同时互连时，一条本来没问题的连接会被误杀，然后重连。


二、场景：A(sid=1) 和 B(sid=2) 同时向对方发起连接
-------------------------------------------------
（比如两边同时开始选举，各自的 WorkerSender 都调用 connectOne）

        A (sid=1)                                              B (sid=2)
  WorkerSender   Listener  RecvWorker_A1         Listener      WorkerSender
      |              |          |                    |               |
 t0   | connectOne(2)|          |                    |  connectOne(1)|
      |-------- TCP 连接 Y (A->B) -------------------> 进入 accept 队列 |
      |              |<----------- TCP 连接 X (B->A) ------------------|
      |              |          |                    |               |
 t1   |              |          |                    |  initiate(X): 目标 1<2
      |              |          |                    |  -> 保留，map[1]=SW_B1(X)   [OK]
 t2   | initiate(Y): 目标 2>1   |                    |               |
      | -> 关闭 Y    |          |                    |               |
 t3   |              | receive(X): 对端 2>1          |               |
      |              | -> 保留，map[2]=SW_A1(X)  [OK]|               |
      |              |          |                    |               |
      |   此时 X 已经是一条两端都认可的正常连接                         |
      |              |          |                    |               |
 t4   |              |          |       receive(Y): 对端 1<2         |
      |              |          |       get(1) = SW_B1(X)  <- 拿到的是刚建好的连接
      |              |          |       SW_B1.finish() -> 关闭 X  [误杀]
      |              |          |       关闭 Y       |               |
      |              |          |       connectOne(1)（在 Listener 线程里同步执行）
      |<---------------- TCP 连接 Z (B->A) ----------|               |
      |              |          |       initiate(Z): 保留，map[1]=SW_B2(Z)
 t5   |              |          | read X 返回 EOF    |               |
      |              |          | finally: SW_A1.finish() -> remove(2)
 t6   |              | receive(Z): 对端 2>1          |               |
      |              | get(2)=null 或 SW_A1（finish 可重入，直接返回）|
      |              | map[2]=SW_A2(Z)  [OK]         |               |


三、各时刻两端的连接状态
------------------------
 时刻 | A.map[2]                      | B.map[1]  | 说明
------+-------------------------------+-----------+------------------------------------
 t1   | -                             | SW_B1(X)  | B 发起的 X 赢得比较，B 保留
 t3   | SW_A1(X)                      | SW_B1(X)  | 已经收敛到 1 条连接 X
 t4   | SW_A1(X)，此时 X 已被对端关闭 | SW_B2(Z)  | B 处理迟到的 Y，误杀了 X
 t5   | 空                            | SW_B2(Z)  | A 发现 X 断开
 t6   | SW_A2(Z)                      | SW_B2(Z)  | 再次收敛到 1 条连接 Z


四、根因
--------
receiveConnection 在 sid < 我 的分支（QuorumCnxManager.java:254-272）里，不管现有连接是不是
刚建好的，都会先 finish 掉。这段逻辑的本意是处理对端重启：对端重启后，本机可能还以为旧连接
是好的（源码注释 "This replica might still believe that the connection to sid is up"）。
但它分不清两种情况：
  - Y 是对端重启后发来的新连接，旧连接确实已经失效，应该关掉；
  - Y 只是和 X 同时发起、晚到一步的重复连接，X 其实是好的。
于是出现了 "建 X、误杀 X、再建 Z" 的抖动。


五、后果
--------
1. X 上正在传的消息可能丢失：SW_B1 已经从 queueSendMap 取出并写进 X 的投票，可能还没被 A 读到。
   好在新的 SendWorker 启动时会先重发 lastMessageSent（:655-657），所以一般只会延迟，不会永久丢失。
2. B 的 Listener 线程会被卡住：t4 时 connectOne(1) 是在 Listener 线程里同步执行的，而且
   connectOne 是 synchronized 的。如果此时 WorkerSender 正持有这把锁去连一台没启动的机器，
   Listener 就要等到那次连接超时（最长 cnxTO），这期间无法接收其他节点的连接。
   这和 toSend 注释里记下的阻塞问题叠加在一起，会让选举进一步变慢。


六、结论
--------
- 3.3.6 能保证的是：每个节点、每个对端 sid，任一时刻最多只有一个活跃的 SendWorker/RecvWorker，
  并且最终收敛到 "大 sid 连小 sid" 的那一条 TCP 连接。
- 竞态带来的不是两条连接并存，而是同时互连时的连接抖动：一条已经正常的连接被误杀后重建，
  期间消息会延迟，Listener 也可能被阻塞。


七、如何复现观察
----------------
同时启动 sid=1 和 sid=2 两个节点，然后在 B 的 DEBUG 日志里找这个顺序：
  "initiateConnection ... established"
  -> "Calling finish on SendWorker"
  -> "Create new connection Back to server: 1"
SendWorker 日志里加的 identityHashCode，正好能区分 SW_B1 和 SW_B2。
